## Windows Smart App Control blocks local ML packages (2026-09-01)

On this machine (Windows 11 Enterprise, likely university-managed), **Smart App Control is fully "On"** (not evaluation mode — confirmed via `HKLM\SYSTEM\CurrentControlSet\Control\CI\Policy\VerifiedAndReputablePolicyState = 1`). This blocks loading of unsigned/unrecognized compiled binaries.

**What's affected**: after installing `torch`, `transformers`, `sentence-transformers`, `bertopic`, `scikit-learn`, `spacy`, `umap-learn`, `hdbscan` — every one of them failed to import, each with `ImportError: DLL load failed ... Eine Anwendungssteuerungsrichtlinie hat diese Datei blockiert` ("An application control policy has blocked this file"). Confirmed via `Microsoft-Windows-CodeIntegrity/Operational` event log (event ID 3077): the specific reason given is that the `.pyd` files "did not meet the Enterprise signing level requirements."

**What's NOT affected**: `numpy`, `pandas`, `matplotlib`, `seaborn`, `jupyter`/`ipykernel`, `scipy` (top-level import only — some submodules like `scipy.linalg._batched_linalg` are blocked when pulled in by sklearn/hdbscan/umap). These packages were evidently already "trusted" by whatever reputation mechanism underlies this (likely Defender's cloud reputation service recognizing common, widely-fingerprinted packages) before this session started.

**Why this isn't fixable by retrying**: unlike the earlier stale-kernel-process issue (where a numpy DLL failed in an old kernel but worked in a fresh process), this block persists across fresh processes for `torch`. Smart App Control's "On" state (vs. "Evaluation") has no user-facing off switch — Microsoft's documented remedy is a clean Windows reinstall, which is not a reasonable step for a course project.

**Decision**: don't fight this — any topic modeling / open-source local classifier work should be deprioritized in favor of the API-based, definition-driven LLM scorer already planned in `Project_Proposal.md` §6.3, since that requires no local compiled ML binaries. See [`notebooks/02_framing_feasibility.ipynb`](../notebooks/02_framing_feasibility.ipynb) for what shipped instead (text-length/logistics heuristics only).

**Workaround note**: `jupyter.exe` itself (the pip-generated console-script wrapper) also intermittently got freshly blocked after installing new packages — it's a tiny stub `.exe` regenerated by pip and apparently needs to be "re-cleared" each time. Running `python -m nbconvert ...` instead of `jupyter nbconvert ...` bypasses the wrapper and avoided the block. Prefer `python -m jupyter ...` / `python -m nbconvert ...` going forward if `jupyter.exe` acts up again.
